## PR #789 — `feat(db): entitlements table per A5 spec (D1=table)`

**Branch:** `feat/entitlements-table-migration`

**CI:** all green (Build and Test, Lint, Validate Rooms, Lighthouse Mobile, Vercel preview).

### What the diff actually does

Creates `public.entitlements` — one row per `(user_id, app_id)` — with:
- `is_premium boolean GENERATED ALWAYS AS (status IN active/trialing/grace_period/past_due) STORED` (the structural fix for the B13 two-derivation class).
- `status text CHECK (...)` + `source text NULL CHECK (...stripe|apple|google|gift_code)` — text+CHECK not native enum (spec §Design decision 2).
- PK `(user_id, app_id)`, `user_id` FK → `profiles(id) ON DELETE CASCADE`, `app_id` default `'mercy_blade'`.
- RLS **enable** + `SELECT`-only GRANT to `authenticated` (no write grant, no write policy) + `entitlements_select_own` policy `USING (auth.uid() = user_id)`.
- Two indexes: partial `(app_id) WHERE is_premium` (MRR/B7), `(computed_at)` (staleness). No standalone `user_id` index (PK prefix already serves it — correct).
- `entitlements_touch_updated_at()` BEFORE UPDATE trigger that bumps `updated_at` only on a `(status, source, expires_at)` delta — `computed_at` and `updated_at` are deliberately distinct clocks (liveness vs change).
- Table comment carrying full provenance.

### Migration order safety

- ✅ **D6 hand-apply note preserved.** Header explicitly: `APPLY VIA SUPABASE SQL EDITOR ONLY — Chau applies, human-reviewed first. … MUST NOT be applied via supabase db push`. Matches PRINCIPLES §4 "Schema migrations on production data" + memory `project_db_schema_drift_audit`.
- ✅ **Tombstone-before-DROP not applicable.** This PR is a CREATE only — no DROP path.
- ⚠️ **Timestamp ordering caveat (already self-disclosed).** `20260519230000` sorts *before* existing later-named migrations in `supabase/migrations/` (max already on main is `20260614000000_profiles_freeze_privileged_columns.sql`). The PR body correctly flags this is immaterial because the migration is Chau-applied via SQL Editor (no `db push` ordered replay) and the file is self-contained + 100% idempotent (`IF NOT EXISTS` / `DROP … IF EXISTS + CREATE` / `CREATE OR REPLACE` / re-runnable `GRANT` / `ENABLE RLS` / `COMMENT`). I verified — no inter-migration dependency violated.
- ✅ **No write GRANT to `authenticated`** + no write policy = `recomputeEntitlement` must use service-role. Matches the "Server-write-only" invariant in the spec and the profiles-freeze defense-in-depth lesson (`20260614000000_*`).
- ✅ **Lossless rollback** documented in header (table is a derived projection of `subscriptions` + gift source; nothing irrecoverable).

### Test coverage

DDL-only — no application code touched, no callers wired yet. No app tests required and none added. Spec ambiguity (`CREATE POLICY IF NOT EXISTS` doesn't exist in any Postgres) correctly resolved by the established `DROP POLICY IF EXISTS + CREATE POLICY` pattern (matches 17 prior repo migrations).

## PR #793 — `fix(webhook): monotonic raw_payload on object quality (per A14)`

**Branch:** `fix/webhook-monotonic-object-quality`
**Files:** 3 (+456 / −2)
- `supabase/functions/stripe-webhook/billing.ts` (+83 / −2)
- `supabase/functions/stripe-webhook/subscription-insert.ts` (+137 / −0)
- `supabase/functions/stripe-webhook/__tests__/rawPayloadObjectQuality.test.ts` (+236 / −0, new file)
**CI:** ✅ all green including the edge-fn Deno type-check, edge-function drift report, vitest 6504/6504. mergeStateStatus: `CLEAN`.

### What the diff actually does

Customer-incident money-path fix. Bug: `subscriptions.raw_payload` was monotonic on time only, so `invoice.paid` (whose Stripe body is an `invoice` object — no `items.data[0].price.unit_amount`) was overwriting the persisted `subscription` body. Result: admin dashboard `amount_cents` reads 0 for every invoice-clobbered row; A15 backfill starved.

Fix mechanism = A14 Option A (smallest-safe-diff):

- New pure helper `resolveMonotonicRawPayload(...)` in `subscription-insert.ts` (the dependency-free, vitest-importable, Deno-clean module — same B5/period-resolution.ts extraction pattern).
- Object-quality rank: `subscription` (3) > `checkout.session` (2) > `invoice` (1) > `other` (0).
- When persisted body is **strictly higher quality** than incoming: keep persisted body BUT stamp it with **incoming** freshness so monotonic ordering for the status/period/price columns is byte-identical to pre-fix. Equal-or-higher incoming still overwrites normally.
- `billing.ts` upsertSharedSubscriptionMonotonic calls the helper at the single upsert convergence point.
- `webhook-events.ts` intentionally untouched (A14 ranked Option A over Option B = invoice-handler rewrite).

Observability: `captureEdgeError` beacon fires **only when a preserved body is actually committed** (the update-success path). Tagged `kind:"observability"`, `stage:"raw_payload_object_quality_preserved"`. Awaited (so the edge isolate flushes Sentry before tear-down) but `captureEdgeError` is internally guarded — zero-cost no-op without `SENTRY_DSN`, never alters webhook response or idempotency.

### Migration order safety

N/A — no migration. Pure edge-function code change.

### Test coverage

Excellent. The new test file (`rawPayloadObjectQuality.test.ts`) is built around the **real prod invoice body that did the clobbering** (`__fixtures__/mylinh-invoice-subscription-cycle.json`, the actual evt_1TV59K event).

- **Anti fake-green proven.** PR body claims:
  - On `origin/main` (fix stashed): `8 failed | 1 passed` — the 1 pass is the **bug-demonstration assertion** (proves the bug exists on main); the 8 failures are fix-dependent.
  - With the fix: `9 passed`. The red→green transition is driven entirely by the fix.
- **Fixture sanity guards.** First test in the suite asserts the fixture *is* an invoice with no `items` and a `lines` array — so future fixture drift can't silently make the rest of the suite pass vacuously.
- **Lifecycle coverage:** invoice-must-not-clobber-subscription, freshness-marker-advance (column ordering unchanged), simulated `sub.created → invoice.paid`, real-sub-update-still-overwrites, invoice-over-invoice (no regression / no fix — A15 backfill's job), first-event-never-preserved.

The "pre-existing webhook tests stayed GREEN through all of this because none of them could import billing.ts (transitively pulls Deno-only `_shared/core.ts`)" is the **exact fake-green failure mode** memory `feedback_testing_discipline` calls out — and the extraction pattern (move the real decision into a dependency-free helper) is the same one used for the B5 bug (`period-resolution.ts`). Right pattern, right scope.

### Contradiction with STRATEGY / PRINCIPLES?

- ✅ **Money-path, customer-incident fix.** PRINCIPLES §3 small narrow PR.
- ✅ **Single chokepoint (upsert convergence) over per-handler rewrite.** Matches CLAUDE.md "Small diffs over smart diffs."
- ✅ **Fail loud / observability.** The Sentry beacon is correctly scoped (only on actual commit), labeled as observability not error, and won't pollute the real error surface. Matches memory `feedback_sentry_triage` (no fake errors).
- ✅ **Historical row repair out of scope** — explicitly handed off to A15's raw_payload backfill SQL (different invoice-typed shape — must read `lines.data[0].pricing` not `items`). Clean scope boundary.

### Risk

Low/medium. The fix is purely additive at one convergence point. The only edge cases worth flagging:

1. **Equal-quality update path.** Real `customer.subscription.updated` events come in with `object: "subscription"` (quality 3); persisted body is also `subscription` (quality 3) → `existingIsHigherQuality` is **false** → the body is overwritten normally. Tested. ✅
2. **`checkout.session` ranking above `invoice`.** Spec choice (A14 §Blast radius). Correctly implemented as quality 2 vs 1. Means a `checkout.session.completed` will NOT be preserved when an invoice arrives later — exactly the intended behavior (checkout-session bodies still carry the right `amount_total`).
3. **Freshness identity check.** Test asserts `persisted.__stripe_freshness === INCOMING_INVOICE_FRESHNESS` via reference equality (`.toBe`) — meaning the helper spreads the existing record but assigns the incoming freshness object as-is. Correct and exactly what the column-ordering invariant requires.
4. **Awaited Sentry beacon on the success path.** `await reportRawPayloadPreservation(...)` runs before `return { stateChanged: true, ... }`. `captureEdgeError` is internally guarded against throwing, but worth noting: if a future change breaks that guarantee, this becomes a webhook-latency path. Currently safe.

### VERDICT: ✅ **MERGE**

No request-changes. The fix is well-scoped, the test is honest (real fixture, red→green proven on `main`), the observability is correctly tagged, and the historical-row repair is correctly handed off to A15.

One heads-up (not a request-change):
- **A15 raw_payload backfill is still required** to repair existing invoice-clobbered rows. This PR only stops new clobbering. PR body says so. Track it separately.

### Ordering with the other 6 awaiting PRs

- Independent of #789 and #792 (different surface — edge function code vs SQL migrations).
- **Should ship promptly** — it's the live money-path fix and `mylinh.nutrition` is the named customer-incident referent. 1 of 9 Stripe subs confirmed affected.
